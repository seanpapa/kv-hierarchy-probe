# Bundled evidence examples

The `baselines/` directory is separate from normalized five-gate evidence. It contains a sanitized
regression summary consumed by `scripts/tools/verify_against_baseline.py`:

| File | Purpose |
|---|---|
| `baselines/transport-english-v1-20260925.json` | Current four-arm, five-context reference for the `transport/english-v1` workload. It is configuration-scoped and is not a portable performance target or direct Gate 1 proof. |

Every file in `evidence/` is a complete normalized evidence document that
`python3 -m kvprobe report` can judge without a GPU, a model, or Docker. They exist so a
reader can see what the five-gate contract accepts and refuses before running anything.

Two kinds of file live here, and the difference matters when reading a verdict.

## Produced from measurement runs

These were generated by `kvprobe ingest` from real measurement output. The measured values and
the gate verdicts below are what the tool concluded from the run files, not something written by
hand. The identifying fields are substituted, and which ones is stated below.

| File | Verdict | Run shape | What it shows |
|---|---|---|---|
| `evidence/attribution-unfiltered-counter.json` | `UNPROVEN`, claims suppressed | Context sweep, 4096 tokens, unified-memory aarch64 host with no native GDS | Captured before the per-device counter reader: the byte counter was not filtered to the tier's device. Bytes match on 10/10 requests, so nothing is violated, but Gate 1 cannot be established: `0/10 target-tier requests have per-request, target-device-filtered byte evidence`. |
| `evidence/gate1-pass-filtered-counter.json` | `PARTIAL`, claims suppressed — Gate 1 and Gate 2 `PASS` | Context run, 4096 tokens, discrete-GPU host: native cuFile GDS arm with its recompute arm, run 1 of the three-run 2026-10-05 re-measurement | The per-device cgroup counter: every request moved the expected 1 GiB on the tier's own disk, so Gate 1 reads `10/10 target-tier requests have per-request, target-device-filtered byte evidence (corroborated)`. Gates 3–5 were not supplied, so the run stays `PARTIAL`. One of nine documents from that run, all of which passed Gates 1 and 2. |
| `evidence/envelope-pass-large-pool.json` | `PARTIAL` | Concurrency sweep 1→8, discrete-GPU host, 6 GiB staging pool | Gate 5 passes, and its result is that `every measured batch met its tier-byte and correctness checks through concurrency 8`; the envelope's upper bound was not reached. Gates 1–4 are `SKIP_UNSUPPORTED` because a concurrency run does not record what they need. |
| `evidence/envelope-collapse-small-pool.json` | `PARTIAL` | The same sweep with a 2 GiB staging pool | At concurrency 8 no measured batch meets its tier-byte check. The sweep is still a valid measurement, so Gate 5 passes; its result is the envelope: `every measured batch met its tier-byte and correctness checks through concurrency 4; above it, 80 of 80 requests were in batches that did not, so they are not credited to the target tier`. The tier counters cover a whole batch, so the result does not say how many of those 80 requests the tier actually missed; that needs the engine log or a per-request counter ([FAILURE-CATALOG §8](../docs/FAILURE-CATALOG.md#tier-stops-under-load) shows one such count from a different run). The validated envelope stays at 4 rather than resuming. |

The last two carry the same `image_digest` because they ran on the same image, and differ in
exactly one configuration parameter — `staging_capacity_bytes` — which is why their configuration
fingerprints differ and why they cannot be merged into one document. They are also the shortest
illustration of what a verdict is for. Both are `PARTIAL` with Gate 5 `PASS`, because both measured
what they set out to measure. The difference between a tier that holds through concurrency 8 and one
that gives up at 4 is in the result, not the verdict.

Host names, model paths, tier paths, container names, the serving software's identity, and the
measured device's identity are replaced with reference values (`/models/reference-32b`, `/tier/reference-gds`,
`/tier/reference-remote`, `reference-build-discrete-01`, `00000000:01:00.0`), and the configuration
fingerprints are those of the substituted values. Every bundled run was taken with
`PROBE_GPU_INDEX=0`, so `gpu_index` is real. The measured values, counter provenance, and gate
outcomes are unmodified.

`image_digest` carries a label rather than a digest here because these runs used images that are
not published. The contract accepts either — see
[Configuration](../docs/CONFIGURATION.md), "Why the serving software is part of the identity" —
and a label is the honest form when the build cannot be disclosed.

The two shapes of `runtime.device_id` are both represented on purpose. The discrete-GPU examples
carry a PCI address, the reference value a platform that prints one would record. The
unified-memory aarch64 example carries `reference-unified-aarch64-0` and omits the optional
`gpu_index`, because `device_id` is an opaque stable identifier rather than a vendor address
format — a platform without PCI addressing stays inside the contract.

No measured document bundled here covers all five gates (see below). The first-visit demo uses it. |
| `evidence/pass-v0.3.json` | `PASS`, claims allowed | The same all-pass path with a legacy Gate 3 block (successful samples only); its Gate 3 result reads `optimistic estimate`. Kept so older evidence stays covered. |
| `evidence/phantom-tier-framework-hit.json` | `FAIL` | Ingested from the synthetic block-tier fixture [`phantom-framework-hit.json`](../tests/fixtures/external/block-tier/phantom-framework-hit.json): the framework reported hits while the tier's device read nothing, so Gate 1 is a measured violation. Not a measurement. |
| `evidence/mixed-configuration-v0.3.json` | `INVALID` | Evidence bound to two verified configurations: a valid record with an unusable verdict. |
| `evidence/pass-capabilities.json` | `PASS` | Synthetic configuration-bound passing evidence for the public reader. |

## Why no bundled measured example passes all five gates

No measured document bundled in this repository combines all five gates. The gates need different
run shapes — a context run for attribution and break-even, an admission-cost run, a capacity sweep,
a concurrency sweep — and a document may only merge runs that share a configuration fingerprint.
The measured examples here each cover selected gates:

- `gate1-pass-filtered-counter.json` reads the tier's device through the per-device cgroup counter,
  so Gates 1 and 2 pass; it holds no admission, capacity or concurrency run, so overall is `PARTIAL`.
- `attribution-unfiltered-counter.json` predates that reader: its host-wide counter leaves Gate 1
  `UNPROVEN`, which is the point it illustrates.
- `envelope-pass-large-pool.json` and `envelope-collapse-small-pool.json` carry no per-request
  attribution, so Gate 1 is unsupported; they illustrate the Gate 5 envelope only.

That is a statement about what this repository bundles, not about the contract. A measured all-pass
example needs a campaign of all five run shapes under one configuration with the per-device reader;
until one is published here, the all-pass example stays labelled synthetic rather than dressed up as
measured. Historical generated examples retain their recorded adapter version rather than being
rewritten as new captures.
